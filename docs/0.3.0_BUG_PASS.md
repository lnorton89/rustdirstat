# 0.3.0: a bug pass over the whole codebase

Not a review of the 0.3.0 diff — that happened twice already, and its
findings are in the commits `fix: six findings from reviewing the
0.3.0 work` and `fix: four findings from reviewing the deferred-item
work`. This is a read of the code the release *did not* touch, on the
principle that a release which adds a second scan root, a live tree and a
command runner changes the meaning of code that was correct before it.

Eight defects, all fixed here, six with a regression test that fails
without the fix. Then the list of what was read and found sound, which is
the part worth having next time: it says where this pass actually went.

## What was wrong

### 1. Quitting either front end erased the user's cleanups

`config::save` writes the whole struct, but neither front end holds the
whole struct: the terminal built a `Config` with five fields set and
`..Config::default()` for the rest, and the window did the same with its
own eight. So quitting the terminal wrote a file with no theme, no
language, no window layout and no inspector position, and quitting either
one wrote `cleanups = []`.

That last one is data loss, not a lost preference. Cleanups are
hand-authored into `config.toml` and exist nowhere else, so writing a
cleanup and then running the app once destroyed it. The feature had been
shipped for exactly as long as the bug had.

`Config::merge_over` lays a partial config over what is on disk —
`Option::or` per field, so a stated `Some(false)` still wins, and
`cleanups` always comes from the file because no front end ever writes
it. `config::save_merged` re-reads at save time rather than keeping the
startup copy, which also makes two front ends run in sequence
last-writer-wins per field instead of per file.

*Tests:* `saving_one_front_ends_preferences_keeps_the_others`,
`a_stated_preference_wins_even_when_it_is_false`.

### 2. The terminal exited when a delete failed

The three filesystem calls in `App::confirm_delete` were the only `?` on
a filesystem operation in the whole terminal, and the error travelled out
through `dispatch`, the event loop and `main`. So a delete refused for
any ordinary reason — no permission, the file open in something else, a
read-only volume, or simply gone since the scan — closed the app instead
of saying why, on the one keystroke where the user is most owed an
explanation. Every other operation in that file already wrote to
`message`.

Now reported, with nothing subtracted from the tree, because nothing was
removed from the disk either.

*Test:* `a_delete_the_filesystem_refuses_is_reported_rather_than_fatal`.

### 3. Duplicate detection found nothing on a multi-root scan

`collect_by_size` built each candidate's real path by walking down from
`tree.root_path`. With more than one root that is not a path at all: it
is the label `Selected locations`. Every candidate came out as
`Selected locations\Users\report.docx`, relative and nonexistent, and the
hasher opened none of them — so the view reported no duplicates and a
pile of unreadable files however many copies the scan actually held.

Each root is now walked against its own path, with the index path seeded
by the root's index so it still addresses the whole tree — which matters,
because Open and Delete resolve those index paths. The rotational-media
check was asking about the label too, and now asks about a real root.

*Test:* `duplicates_are_found_across_several_roots`.

### 4. The window's CSV export wrote label paths

Same bug, second site. `write_tree_csv` exists precisely for this and the
CLI and the terminal both call it; the window called `write_csv_to_file`
with `tree.root_path`, so every row of a multi-root export named a place
that does not exist — in the file whose only purpose is to be read by
something else.

### 5. The Windows maintenance tools were handed `\\?\C:`

`volume_root_arg` returned the first path component's text. The scan
roots are canonicalized, so on Windows that component is the *prefix*,
and `chkdsk \\?\C:` and `vssadmin ... /for=\\?\C:` are both refused. The
two tools that take a volume had therefore never worked on a path the app
produces. The drive letter is now read off the prefix rather than printed
with it, and `C:\` and `\\?\C:\` answer identically.

*Test:* `a_volume_argument_is_a_drive_letter_however_the_path_is_spelled`.

### 6. The extended-length prefix reached everything except the filesystem

`util::display_path` exists because `\\?\C:\Users\...` is the correct
thing to hand a file API and the wrong thing to show a person. It was
being used for headings and tooltips and skipped everywhere else:

- **The shell launcher.** `explorer \\?\C:\Users\someone` does not open
  that folder — the prefix is an instruction to the Win32 path parser,
  which the shell does not run. Open and Reveal were both affected.
- **The clipboard.** What Copy Path produced went into somebody else's
  address bar or command line, and most of them refuse that spelling.
- **The text report**, whose first line opened with it.
- **The CSV export**, in every row.
- **Every status line** naming a deleted, emptied or exported path.

All of them now go through `display_path`. The filesystem calls are
untouched and still use the canonical form.

### 7. A relative directory symlink was recreated as a file symlink

Windows has two symlink calls and the cross-device move fallback picked
between them with `link_target.is_dir()` — of a target like `../shared`,
which resolves against the *process working directory* rather than the
link's. A relative directory link was recreated with the wrong call and
arrived broken. It asks the source link instead, which the filesystem
resolves the way the link means it.

*Test:* `a_relative_symlink_keeps_its_relative_target` (Unix; the choice
itself can only be exercised on Windows, where a test cannot create a
symlink without elevation, so what the test pins is that the target is
written through unchanged).

### 8. A rescan of a multi-root scan sent the terminal back to the top

`restore_path` descended from `tree.root_path` — the label again — so
every candidate it built matched nothing and the browser fell back to the
root however deep the user had been.

*Test:* `a_rescan_restores_the_position_inside_one_of_several_roots`.

## The shape of what was found

Six of the eight are one of two mistakes:

- **A label used as a path.** Multi-root scans put a display string where
  a `PathBuf` goes, and the type system cannot tell them apart. Four
  sites: duplicates, the window's CSV export, the terminal's rescan
  restore, and the folder dialog's starting directory. The two that were
  already correct — the CLI export and the terminal's — were fixed during
  the sprint-4 review, which is exactly why the rest were worth looking
  for.
- **A canonical path shown to something that is not the filesystem.**
  Five sites, all listed above.

Both are cases where a value is correct for its original use and wrong
for a use added later. If a third arrives, that is the pattern to grep
for: `root_path` reaching anything that opens a file, and `.display()` on
a path reaching anything a person or another program reads.

## Read and found sound

So the next pass knows where this one went:

- `search.rs` — the glob-to-regex translation, including the nesting and
  the unterminated-brace fallbacks, and the off-by-one between
  `MAX_RESULTS` and `truncated`.
- `top_files.rs` — the bounded heap, including `k = 0`.
- `model.rs` — `walk_preorder`'s frame discipline (the root frame's
  missing segment is handled correctly), `Node::drop`'s drain, and the
  exact-versus-forgiving split across `path_for` / `node_for` /
  `deepest_valid_*`.
- `config.rs` — per-field forgiveness, and the atomic temp-file-and-rename
  save.
- `cleanups.rs` — substitution (unknown placeholder and trailing `%` are
  both errors), and the argv-only launch. One thing the threat model did
  not cover is now in it: on Windows a bare program name is resolved
  against the process working directory before `PATH`.
- `util.rs` — the cross-device gate on the move fallback, the
  enumerate-fully-then-delete discipline in `empty_directory_to_trash`,
  and `preserve_metadata`'s ordering (directory timestamps written after
  the walk, not during it).
- `stats.rs`, `csv_export.rs`, `report.rs` — the aggregate reads and the
  two multi-root writers.
- The window's `confirm_delete`, which already reports rather than
  propagates, and already re-checks the name and kind before handing a
  path to `remove_dir_all`.

## Not read

The parts of the window that only draw: `gui/ui/treemap.rs`,
`categories.rs`, `extensions.rs`, `theme.rs`, `widgets.rs`. They are
covered by the rendering tests in `gui/ui/tests.rs`, which click real
recorded rects, and a defect there is visible rather than silent. The
scanner's Windows listing path and the FFI in `platform.rs` were reviewed
during sprint 3 and are not re-read here.

# 0.3.0: a review of the release's own changes

The pass above deliberately looked *away* from the diff. This one looks
at it: all 24 commits, 64 files, about 10,800 added lines, including the
parts the pass above listed as not read. Six defects, all fixed, two of
them guarded by a new check that would have caught the class.

## What was wrong

### 1. The Windows listing borrowed a name at an alignment it refused to assume

`platform::for_each_entry` reads each `FILE_ID_BOTH_DIR_INFO` with
`read_unaligned`, saying in its own comment that record alignment is
"documented but not enforceable here" — and then built the filename with
`slice::from_raw_parts::<u16>`, which requires exactly that alignment.
`offset` advanced by `NextEntryOffset` with only a bounds check, so a
driver reporting an odd offset produced a misaligned `*const u16`, which
is undefined behaviour rather than a wrong answer.

The fix is to check what is relied on, which is the stance the rest of
the function already takes toward `FileNameLength`: a `NextEntryOffset`
that is not a multiple of 8 abandons the listing, and `name_at` is
checked even before the slice is built. Both are one comparison per
entry against a syscall's worth of work.

### 2. macOS notarisation submitted a format Apple does not accept

`notarytool submit` takes `.zip`, `.pkg` and `.dmg`. The step handed it
`rustdirstat-<tag>-<target>.tar.gz`, because the macOS release archive is
a tarball for the same reason the Linux one is. The step is gated on a
secret that is not set, so it has never run — it would have failed the
first release that had certificates, which is the one thing the roadmap
says is left to do.

A notarisation ticket is issued against the *binaries* inside the
submission, not against the container, so what ships and what is
submitted need not be the same file. A throwaway `ditto -c -k` zip of the
staging directory the Package step already built goes to Apple; the
tarball that ships is unchanged, and the zip is deleted.

### 3. Ten string literals rendered with a gap in the middle of a sentence

A multi-line Rust string joins its lines with a trailing `\`. Without it
the newline *and the source indentation* become part of the text:

```text
"This is how                              much of the total is..."
```

That was the status bar's hard-link tooltip. Also both paragraphs of the
Cleanups settings page, its empty state, a message in the terminal, and
five test assertions. Nothing caught it — it is valid Rust, `rustfmt`
does not reformat inside a literal, and clippy has no opinion about
prose.

`tests/source_hygiene.rs` looks now. Six or more spaces between two words
inside a source line is the signature, and it is narrow enough to leave
the deliberate column alignment in `header_check`'s header fixtures
alone.

### 4. Seven catalogue keys nothing asked for

`assets/lang/en.toml` defined `status.scan_complete`, `status.scanning`,
`status.busy`, `status.scan_cancelling`, `status.hard_links`,
`status.hard_links_hover` and `settings.language` — and beside each of
them the code held the English literal. So a German user saw a translated
menu bar above an English status bar, and a translator who translated
those seven lines saw no effect anywhere.

`every_key_the_code_uses_is_in_the_catalogue` only ever checked one
direction: a key the code invents must exist. The opposite is quieter and
was therefore worse, so `every_key_the_catalogue_defines_is_asked_for`
now checks it. Three further keys were added for the strings beside them
(`status.scanning_folder`, `status.hashing`, `status.running_tool`) —
leaving one arm of `busy_text` translated and two not would have been the
same defect one level down.

### 5. An installed build had no way to obtain a catalogue to translate

The English catalogue is `include_str!`'d into the binary, and
`assets/lang/` ships in no `.deb`, no `.rpm` and no release archive. The
Appearance page said "a translation is a copy of the catalogue below" and
then offered a folder path — not a catalogue. The only way to obtain one
was to clone the source, which is not a thing a translator does.

`i18n::write_starter_catalogue` writes the compiled-in English catalogue
into that folder as `en.toml`, behind a button on the same page.
`en.toml` is the one name `available()` skips and `set_language` never
reads, so it is unambiguously a template to be renamed rather than a
translation that takes effect where it lands. `assets/lang/de.toml`
remains what it always was — a worked example in the repository, not a
shipped translation.

### 6. The hard-link figure was on-disk bytes labelled by the size toggle

The ledger recorded `entry.physical`, and the status bar rendered it
through `size_label(shared, app.use_physical)` — which appends
"(physical)" only when the toggle is on. So with the window showing
logical sizes the line read "1.2 GB · 340 MB shared by hard links", two
units in one sentence with the second labelled as the first. Toggling
moved the total and not the correction, which was the visible symptom.

`HardLinks` keeps both running totals now and `Tree::hard_link_bytes` is
a `SharedBytes`, whose `effective(physical)` mirrors
`Node::effective_size` because it answers the same question about the
same toggle. Both front ends ask it.

## Read and found sound

The scanner's core is the strongest part of the release. `stream_root`
publishes through a `Sync` sink while numbering under one lock; the
collecting and streaming walks share `Totals`, so a live tree and its
finished self cannot drift apart on arithmetic; `MAX_PARALLEL_DEPTH`
hands off to an iterative walk before user-chosen depth reaches the
stack; `scan_dir_deep`'s frame discipline is right, including its cancel
and root-frame cases. `EntryInfo::from_listing`'s `links: 1` really is
unreachable — `directory_listing` returns `None` off Windows.
`for_each_entry` discards a partial listing rather than reporting one.
The live-tree handoff in `gui/app/scan.rs` defers correctly on a shared
`Arc` in both `drain_pending_children` and `finish_live_tree`, and
`replace_tree` dropping `pending_delete` at the one place trees are
swapped is the right place for that guard. `open_directory` asking for
`FILE_LIST_DIRECTORY` rather than `GENERIC_READ`, and `system_time`'s
fully checked arithmetic, are both better than they had to be.

## Noted, not changed

- **Nested and duplicate roots are accepted.** Scanning `C:\Users` and
  `C:\Users\Lawrence` together counts the overlap twice in every total
  and against the volume's free space. Duplicate detection is unaffected
  (the two names share an inode, so the group is correctly not
  reclaimable). Rejecting the combination is a separate decision about
  what a multi-root scan means.
- **`Category::label()` is English.** The nine category names stay in
  English in both front ends, including the inspector's Type row, which
  is otherwise fully translated. Part of the localization remainder in
  [`ROADMAP.md`](ROADMAP.md).
- **`Totals::add`/`merge` use bare `+=`** where `combine` beside them
  uses `saturating_add`, and both index `ext_totals[category.index()]`
  where the rest of the crate uses `get_mut`. Neither is reachable —
  a filesystem cannot overflow `u64` bytes and the index is bounded by
  construction — so this is a consistency note, not a defect.
