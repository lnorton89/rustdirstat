I reviewed the actual **`v0.2.1` release tag**, not just current `main`.

# Release-quality issues

## 1. The `v0.2.1` tag contains the wrong changelog state

This is the biggest concrete release problem.

At the actual `v0.2.1` tag, all of the 0.2.1 work is still listed under:

```markdown
## [Unreleased]
```

There is no:

```markdown
## [0.2.1] - 2026-08-21
```

section in the tagged source.

Only **after** the tag was created did PR #3 regenerate the changelog so current `main` contains the correct:

```markdown
## [0.2.1] - 2026-08-21
```

section with the categorized release entries.

That means GitHub's automatic:

```text
Source code (zip)
Source code (tar.gz)
```

for `v0.2.1` permanently contain a changelog claiming the released changes are still unreleased.

The current documented process—**tag first, regenerate changelog afterward**—causes this by design.

### Recommended fix for future releases

Prepare the release section first:

1. generate the changelog for the target version;
2. commit it;
3. verify CI;
4. place the version tag on that exact commit;
5. push the tag;
6. let the release workflow build from that immutable tag.

Do not regenerate the released changelog section only after tagging.

## 2. The SBOM/provenance setup overstates what is attested

The workflow comment says:

> Signed build provenance for every asset

but the attestation step only includes:

```yaml
subject-path: |
  dist/*.zip
  dist/*.tar.gz
  dist/*.deb
```

It does **not** attest:

```text
*.sha256
*-sbom.cdx.json
```

More importantly, the CycloneDX SBOM is merely uploaded as another file. It is not cryptographically bound to the release artifacts as an SBOM attestation.

The current setup is still useful—the primary archives and `.deb` receive provenance—but the workflow comments describe broader coverage than it actually provides.

### Recommended improvement

Use GitHub's attestation support so the SBOM is attached as an actual SBOM attestation rather than only as a release attachment.

That makes the relationship explicit:

```text
release artifact
    ↓
signed provenance
    ↓
associated CycloneDX SBOM
```

The workflow comments should also accurately say which assets are attested.

## 3. Release-building tools are not version-pinned

The workflow carefully pins GitHub Actions to immutable commit SHAs, but then installs:

```bash
cargo install cargo-deb --locked
cargo install cargo-cyclonedx --locked
```

`--locked` does **not** pin which release of those tools is installed.

A future re-run of the exact same `v0.2.1` workflow could install newer versions of:

```text
cargo-deb
cargo-cyclonedx
```

and potentially:

- produce different package output;
- change SBOM structure;
- behave differently;
- stop building with the pinned Rust version.

That is inconsistent with the otherwise strong reproducibility/supply-chain approach.

### Recommended fix

Pin exact known-good tool versions:

```bash
cargo install cargo-deb   --version <known-good-version>   --locked

cargo install cargo-cyclonedx   --version <known-good-version>   --locked
```

Then upgrade those versions intentionally through normal repository changes.

# Product-semantics issue: Windows "physical size"

Windows physical-size handling is now deliberately defined as:

```text
sparse/compression-aware size
```

rather than true allocation-cluster consumption.

The source explicitly documents that a plain:

```text
1-byte file
```

reports:

```text
1 byte
```

rather than something like:

```text
4096 bytes
```

for a filesystem with 4 KiB allocation units.

That makes the implementation internally consistent, and the `GetCompressedFileSizeW` error handling issue from the previous review has been corrected.

However, the README still describes the feature as:

> Logical vs. physical (on-disk) size

That wording can imply actual allocated filesystem space.

For a WinDirStat-style disk-usage application, I would prefer one of two approaches:

### Option A — implement true allocated size

Use Windows allocation-size information, such as the `AllocationSize` field available through the appropriate file-information APIs.

This would make Windows physical-size accounting conceptually match Unix:

```text
logical size
vs.
allocated filesystem blocks
```

### Option B — keep current semantics but rename it

If avoiding a handle/query per ordinary file is a deliberate performance decision, describe the mode more precisely.

For example:

```text
Logical / compressed size
```

or document clearly in the UI that Windows physical mode is compression/sparse-aware rather than cluster-allocation-aware.

# Bottom line

I **would not pull or reissue `v0.2.1`** over these findings.

The actual application release is solid, and the dangerous filesystem/destructive-operation defects that originally dragged correctness and safety down to roughly 5.5/10 are now gone.

The remaining issues are predominantly release-process quality rather than application-integrity problems.

For **v0.2.2**, I would prioritize:

1. finalize and commit the changelog **before** creating the release tag;
2. pin `cargo-deb` and `cargo-cyclonedx` versions;
3. turn the CycloneDX file into a real SBOM attestation;
4. make attestation comments accurately describe their coverage;
5. eventually decide whether Windows "physical size" should mean true allocation size or keep the current compression/sparse-aware definition with clearer UI wording.

That would push the release side much closer to the quality level the application code has now reached.
