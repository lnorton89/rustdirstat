This is considerably better engineered than a typical v0.2 utility. The architecture, large-tree thinking, regression testing, documentation, and effort to eliminate hidden failure modes are strong.

# Release blockers

## P0 — Filenames are stored lossily, so filesystem operations can target the wrong path

This is the most important defect I found.

`Node.name` is a `String`.

During scanning, real filesystem names are converted with:

```rust
entry.file_name().to_string_lossy().to_string()
```

Later, `Tree::path_for()` reconstructs real filesystem paths by pushing those stored names back onto the root path.

That is not safe on Unix. Unix filenames are byte strings, not necessarily UTF-8. `to_string_lossy()` replaces invalid byte sequences with U+FFFD.

That means two distinct real filesystem names can collapse to the same `String`.

Conceptually:

```text
actual filename A: foo<invalid-byte>bar
stored name:       foo�bar

actual filename B: foo�bar
stored name:       foo�bar
```

The tree can distinguish them by child index, but once an operation reconstructs the filesystem path, that distinction is gone.

That affects:

- Delete
- Permanent delete
- Empty-folder actions
- Move
- Open
- Reveal
- Duplicate hashing
- CSV path reconstruction
- Copy path

For a disk-usage viewer this would be an accuracy defect. For an application with `remove_dir_all`, it is a safety defect.

### Fix

Filesystem identity should remain lossless throughout the model:

```rust
pub name: OsString
```

Display boundaries should perform the lossy conversion:

```rust
name.to_string_lossy()
```

Anything that touches the filesystem should remain `OsStr`/`OsString`/`Path`.

This needs to propagate through:

- `Node`
- scanner
- `Tree::path_for`
- `PendingDelete`
- sorting
- extension extraction
- search
- duplicate collection
- row rendering
- reports/CSV

Display/search can have an independently generated presentation string if necessary. **Never derive an operational path from presentation text.**

I would not ship another release with permanent deletion enabled until this is corrected.

## P0 — Moving a directory inside itself can trigger recursive copy explosion

`move_path()` currently works like this:

1. reject an existing destination;
2. try `rename`;
3. on **any** rename failure, assume a copy/delete fallback is appropriate;
4. recursively copy directories;
5. delete the original.

Consider:

```text
source = /data/archive
dest   = /data/archive/moved
```

`rename()` cannot move a directory underneath itself.

The fallback then creates:

```text
/data/archive/moved
```

and proceeds to enumerate:

```text
/data/archive
```

It can now discover its own newly created destination and start producing:

```text
/data/archive/moved/moved
/data/archive/moved/moved/moved
...
```

until path limits, disk limits, or another filesystem error terminates it.

There is a second design flaw here: **every rename error triggers copy fallback**. Permission failures, invalid names, access-denied errors, source/destination relationships, etc. are not evidence that the source is on another filesystem.

### Fix

Before doing anything:

```text
canonical source
canonical destination parent

reject if destination lies within source
```

Then only perform copy/delete fallback for the actual cross-device error:

- Unix: `EXDEV`
- Windows: `ERROR_NOT_SAME_DEVICE`

Everything else should preserve and return the original rename error.

This should have regression tests for:

```text
a -> a/b
a -> a/b/c
a -> a
a -> existing destination
cross-device file
cross-device directory
permission-denied rename
```

# High-priority correctness problems

## P1 — GUI rescan restoration does not actually restore by filesystem path

Your TUI gets this right.

The TUI explicitly reconstructs the browsing location by matching filesystem path components because:

> node indices aren't stable across scans

The GUI does something different.

After replacing the tree, it retains the previous `zoom_path` and `selected_path` by feeding their raw child indices into `valid_prefix()`.

That only answers:

> Do indices `[4, 7, 2]` still exist?

It does not answer:

> Do indices `[4, 7, 2]` still refer to the same directory?

Filesystem enumeration is not stable between scans, and your scanner does not create a persistent canonical sibling order before storing children.

The dangerous case is not a child disappearing. You handle that.

It is:

```text
old index 4 = Downloads
new index 4 = Documents
```

`valid_prefix()` happily considers index 4 valid.

The GUI can therefore silently restore selection or zoom to a different filesystem object.

The source even correctly explains why pending deletes cannot cross a rescan:

> an index path only means anything against the tree it was taken from

but then immediately carries navigation index paths across the same tree replacement.

### Fix

Before starting/replacing a scan, capture the location as lossless relative filesystem components.

After the new tree arrives:

```text
["Users", "larry", "Downloads"]
```

should be resolved against the new tree to generate new child indices.

Do the same for:

- zoom
- selected item
- expansion state, where practical

Do not transport `Vec<usize>` across tree identity.

## P1 — “Empty folder” can silently leave files behind and still report success

GUI:

```rust
for child in std::fs::read_dir(&path)?.filter_map(Result::ok) {
    trash::delete(child.path())?;
}
```

This silently discards individual `ReadDir` errors.

That means a directory can contain:

```text
file A      successfully enumerated
file B      enumeration error
file C      successfully enumerated
```

and RustDirStat will trash A and C, silently ignore B, and report:

```text
Emptied: ...
```

Your scanner is actually more careful than this: it explicitly counts individual directory enumeration failures because a partial listing must not masquerade as a complete one.

The destructive path should be at least as strict as the read-only scanner.

There is also a partial-failure problem:

```text
delete child 1 succeeds
delete child 2 succeeds
delete child 3 fails
```

At that point the filesystem has changed even though the operation returns an error.

### Fix

Do not use `filter_map(Result::ok)` in filesystem mutation code.

First enumerate all immediate children and fail if enumeration is incomplete. Then perform deletions while tracking individual results.

For filesystem mutation, the safest model strategy is:

```text
perform operation
rescan affected directory/tree
```

rather than trying to infer final state after a partially successful sequence.

## P1 — `DirEntry` retention can exhaust Unix file descriptors

`read_entries()` reads an entire directory into:

```rust
Vec<std::fs::DirEntry>
```

Those entries are then retained while recursive child scans are performed. The deep-tree iterative implementation likewise retains an `IntoIter<DirEntry>` in every active stack frame.

This has a non-obvious Unix consequence.

Rust documents that a Unix `DirEntry` contains an internal reference to the open directory, so holding `DirEntry` values can keep directory file descriptors open.

With a deep or highly parallel tree, this can create a large number of simultaneously open directory handles and eventually hit `RLIMIT_NOFILE`.

### Better scanner representation

Consume `DirEntry` before recursion:

```rust
struct EntryInfo {
    name: OsString,
    path: PathBuf,
    metadata: Metadata,
}
```

Then drop all `DirEntry` handles before descending.

This also solves half of the P0 filename problem naturally.

## P1 — Hard links make disk usage and “reclaimable duplicates” wrong

On Unix, physical size is calculated using:

```text
st_blocks * 512
```

for every scanned directory entry.

No `(device, inode)` identity is tracked.

Duplicate detection similarly treats each pathname as an independent file and hashes all same-sized candidates.

The UI then computes reclaimable duplicate space as roughly:

```text
size × (number of copies - 1)
```

For hard links:

```text
foo.iso
bar.iso
baz.iso
```

may all refer to the same inode and same allocated blocks.

RustDirStat can:

- count the allocated storage multiple times;
- report them as byte-identical duplicate files;
- claim deleting two would reclaim `2 × size`;
- actually reclaim zero bytes until the final hard link disappears.

### Fix

Introduce platform file identity.

Unix:

```text
(st_dev, st_ino)
```

Windows:

```text
volume serial + file ID
```

At minimum, duplicate detection needs to distinguish:

```text
duplicate content
hard-link alias
```

Ideally physical-size accounting should also define a policy for hard links rather than blindly summing each directory entry.

## P1 — Whole-volume Unix scans can cross filesystem boundaries

The scanner follows every real directory it encounters. I did not find a same-filesystem/device guard in the traversal.

On a Linux scan of:

```text
/
```

that potentially includes:

```text
/proc
/sys
/dev
/run
/mnt/other-drive
/media/USB
network mounts
bind mounts
```

Meanwhile, `Tree.volume_free` and `volume_total` refer to the volume containing the original root, and the treemap specifically reasons about that volume's free space.

That creates two problems:

1. potentially pathological scans;
2. filesystem bytes from multiple volumes compared with free space from one volume.

### Fix

Track the root filesystem identity.

Default whole-drive scans to:

```text
stay on root filesystem
```

with an explicit option equivalent to:

```text
--cross-filesystems
```

On Unix this is straightforward using `st_dev`.

# Performance problems

## P1 — GUI search is synchronous over the entire tree

The GUI properly backgrounds:

- initial scans;
- rescans;
- duplicate hashing;
- Windows maintenance tools.

But search does:

```rust
let outcome = search::search(&self.tree.root, &self.search.query);
```

directly from GUI state handling.

Your own performance document uses a real reference workload of approximately:

- 8.95 million files
- 1.34 million directories
- 10.3 million `Node`s
- >2 GB resident memory

An O(10 million nodes) search on the egui frame thread is a freeze.

The search walker itself is sensibly iterative. The problem is where it runs.

### Fix

Search should use the same worker/channel pattern already present for duplicates and scanning.

It should also support cancellation/debouncing if search becomes live-as-you-type later.

---

## P1 — Extension aggregation recursively walks the tree on the UI thread

`collect_extensions()` recursively descends through every child directory.

`refresh_extensions()` invokes it for the current zoom subtree.

That causes two problems.

First, zooming a large subtree or changing physical/logical mode can block the frame thread.

Second, this violates one of the best architectural rules elsewhere in the project: filesystem-tree depth is controlled by the user, so tree-sized walks should not recurse.

You fixed this exact class of issue in:

- scanner deep tail
- search
- top files
- duplicate collection
- CSV
- `Node::Drop`

but this one remains.

### Fix

At minimum, make extension collection iterative.

For responsiveness, calculate it asynchronously for large subtrees or maintain sufficient aggregated data during scanning.

---

## P2 — GUI directory-row flattening also recursively follows expanded depth

`push_tree_rows()` recursively calls itself for expanded directories.

Normal users will never expand 10,000 levels manually, so this is much less urgent than scanner recursion.

It is still inconsistent with the codebase's explicit depth-safety policy.

Make this iterative eventually.

# Duplicate-file subsystem

The overall design is good:

```text
size prefilter
→ whole-group candidate cap
→ parallel BLAKE3
→ deterministic result sorting
```

The candidate-limit handling is particularly good. It deliberately refuses to hash half of one size group because doing so would produce misleading duplicate counts.

There are still two significant shortcomings.

## Hash/read failures disappear silently

This code:

```rust
hash_file(&path).ok()
```

means a file that:

- disappears;
- becomes unreadable;
- produces an I/O error;

simply vanishes from duplicate results.

The result distinguishes files skipped because of the candidate cap, but not files skipped because they could not actually be hashed.

`DupScan` should contain something like:

```rust
pub skipped_by_cap: usize,
pub read_failures: usize,
pub changed_files: usize,
```

The UI should not present the result as complete when it was not complete.

## Parallel hashing can be hostile to spinning disks

Rayon parallel hashing is excellent for CPU throughput but duplicate detection is normally storage-bound.

Eight workers randomly reading eight giant files from a HDD can be substantially slower than a low-concurrency sequential stream.

A bounded duplicate hashing concurrency of perhaps:

```text
SSD/NVMe: several workers
HDD: 1–2 workers
```

would be worth benchmarking.

This is optimization rather than correctness.

# Windows-specific problems

## P1 — `vssadmin delete shadows` arguments are wrong

The implementation passes:

```rust
[
    "delete",
    "shadows",
    "/for",
    &volume,
    "/all",
    "/quiet"
]
```

Microsoft documents the syntax as:

```text
vssadmin delete shadows /for=<ForVolumeSpec> ...
```

not `/for` as one argument followed by the volume as another.

So this should be generated as one argument:

```text
/for=C:
```

There is also a product-description accuracy issue: the app says this deletes every shadow copy on the volume, while Microsoft describes `vssadmin delete shadows` as deleting **client-accessible** shadow copies.

For an irreversible maintenance command, wording should be exact.

---

## P2 — “Physical size” is not physical size on Windows

On Unix:

```text
physical = st_blocks × 512
```

On non-Unix, including Windows:

```rust
meta.len()
```

The code comments explain why: getting allocated NTFS size requires another syscall per file.

That engineering choice is understandable.

The UI problem is that the feature is still presented as:

> physical (on-disk) size

On the operating system most closely associated with WinDirStat, the toggle therefore gives identical logical and physical values, even for sparse/compressed files where the distinction is specifically useful.

Either:

1. implement actual Windows allocated size; or
2. mark physical-size information unavailable on Windows and disable/rename the toggle there.

Returning logical size silently is technically convenient but product-wise misleading.

---

## P2 — Cross-device move fallback loses filesystem metadata

The copy fallback preserves contents and symlinks, but normal `std::fs::copy`/directory recreation is not a complete filesystem-object migration.

Depending on platform, that can lose:

- timestamps;
- ACL/security information;
- extended attributes;
- ownership;
- alternate metadata.

For a cleanup utility, a user choosing “Move” reasonably expects filesystem-manager semantics.

The simplest robust approach may be to use native platform move/copy facilities rather than maintaining a miniature cross-platform file manager internally.

# Model/API design

## P2 — `node_for()` and `path_for()` silently truncate invalid paths

The design intentionally makes these return the deepest node that still exists if an index path becomes invalid.

You later added `try_node_for()` for operations where stale identity matters.

I would invert this API.

For a filesystem application:

```rust
node_for() -> Option<&Node>
path_for() -> Option<PathBuf>
```

should be exact.

Then explicitly name the forgiving operation:

```rust
deepest_valid_node()
valid_prefix()
```

The dangerous behavior should require an intentionally dangerous-looking API, not be the default.

`confirm_delete()` already demonstrates why exact lookup matters.

# CLI review

## P2 — Supposedly mutually exclusive modes are not mutually exclusive

The crate describes TUI, report, and CSV as mutually exclusive modes.

But the CLI defines independent:

```text
--no-tui
--csv <path>
```

and then gives CSV precedence.

So:

```bash
rustdirstat --no-tui --csv out.csv .
```

is accepted and silently means CSV.

Use Clap conflicts:

```rust
#[arg(conflicts_with = "csv")]
no_tui: bool
```

or an `ArgGroup`.

Add an integration test beside the existing real-binary CLI tests. Those tests are otherwise a strong part of the repository.

# Architecture

This is one of the repository's strongest areas.

The high-level split is correct:

```text
filesystem
    ↓
scanner
    ↓
Tree / Node
    ↓
shared analysis/layout
   ↙       ↘
 TUI       GUI
```

Especially good decisions:

- GUI and TUI share the model instead of independently implementing disk semantics.
- Sorting moved into the model after the implementations drifted.
- Search/top-files moved out of the TUI when they were recognized as general model operations.
- Treemap geometry is shared while presentation-specific traversal remains frontend-specific.
- Windows-specific functionality is isolated.
- Background tree destruction acknowledges that deallocating millions of individual heap objects can itself freeze a GUI.
- `Tree::placeholder` allows the window to exist while scanning.
- Long work reports back through channels rather than sharing mutation-heavy state.

The code has clearly been refactored from observed bugs rather than constructed around theoretical abstractions. That generally produces better boundaries.

# Scanner design

The scanner has several unusually good details.

It caps recursive parallel traversal at 64 levels and switches to an iterative walk for the deep tail.

That is a sensible compromise between:

```text
parallel breadth near root
```

and:

```text
bounded stack depth deep down
```

It also distinguishes:

```text
could not open directory
```

from:

```text
opened directory but individual enumeration entries failed
```

and propagates unreadable counts.

That is exactly the kind of detail a disk-usage analyzer needs.

Once the `DirEntry` lifetime and filename-identity issues are fixed, the scanner will be one of the stronger parts of the project.

# Memory/performance design

The performance documentation is excellent.

You are designing against an actual pathological workload rather than “this directory with 40,000 files felt fast on my laptop.” The documented reference scan is roughly 10.3 million nodes and >2 GB resident memory.

Strong choices include:

- no full `PathBuf` per node;
- iterative node destruction;
- background destruction of old huge trees;
- derived cache keys instead of manual invalidation;
- bounded treemap tile count;
- lower-quality interactive treemap while dragging;
- level-order treemap detail allocation;
- streaming CSV output;
- bounded duplicate candidates;
- event-driven TUI rendering;
- batched progress atomics.

The treemap work in particular is more careful than most applications of this kind. The code considers coverage correctness, child truncation bias, rounding, label reservation, geometry containment, and detail budgets rather than merely implementing `squarify()`.

The synchronous GUI search and extension walk stand out precisely because the rest of the performance design is so disciplined.

# Release workflow security

## P1 — Write-capable release workflow runs mutable third-party Actions

The release workflow declares:

```yaml
permissions:
  contents: write
```

at workflow level and then invokes third-party actions using mutable references including:

```text
actions/checkout@v4
dtolnay/rust-toolchain@master
Swatinem/rust-cache@v2
```

Particularly concerning is:

```text
dtolnay/rust-toolchain@master
```

because `master` explicitly means “whatever commit upstream currently puts there.”

For a workflow holding a release-writing token, dependencies should be immutable.

### Better design

Pin every Action to a full commit SHA.

Also split privileges:

```text
build jobs:
    contents: read

publish job:
    contents: write
```

Build jobs can upload ordinary workflow artifacts.

The final publishing job can download those and create/upload the release assets.

That significantly reduces supply-chain blast radius.

# Nix

The flake is thoughtful, especially around runtime-loaded winit/wgpu libraries.

There is one conceptual mismatch.

The repository strongly asserts that `rust-toolchain.toml` pins local and CI development to Rust 1.98.0.

But the Nix development shell explicitly installs:

```text
pkgs.cargo
pkgs.rustc
pkgs.clippy
pkgs.rustfmt
```

from the flake's nixpkgs input, which points at `nixos-unstable`.

Inside that shell, those Nix-provided executables can supersede rustup and therefore defeat the repository's single-toolchain assumption.

Use a Rust overlay/fenix setup derived from the same version as `rust-toolchain.toml`, or otherwise make the Nix shell use the exact pinned toolchain.

- linked directory/extensions/treemap views;

- search;
- largest files;
- duplicate detection;
- trash and permanent deletion;
- move/open/reveal/copy;

- configurable themes;
- resizing/orientation;
- background scanning;
- persisted display preferences.

The WinDirStat-parity approach is also sensible: preserve the useful interaction model without being trapped into a pixel-for-pixel clone.

The biggest product problem is not missing features. It is **trust**.

This app is allowed to say:

```text
Permanently delete
Empty folder
Move
Delete all shadow copies
```

Once an application exposes those operations, obscure filename semantics and stale identity handling become higher priority than another view or theme.

I would shift the next development cycle toward filesystem correctness rather than adding features.

## Bottom line

The project already has the difficult parts of a good architecture: coherent boundaries, real regression tests, large-data thinking, and careful UI performance work. It does **not** need a broad rewrite.

It needs a focused filesystem-integrity pass.

The main conceptual change is this:

> **A display name, a tree position, and a filesystem object's identity are three different things.**

Right now `String` names and `Vec<usize>` index paths sometimes serve more than one of those roles. Most of the highest-severity defects flow directly from that. Separate them cleanly—lossless names for filesystem identity, index paths only within one immutable tree generation, strings only for presentation—and the safety level of the entire application rises substantially.
