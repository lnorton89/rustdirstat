# 0.3.0 sprint plan

The two releases before this one were both reactions to a review.
`v0.2.1` implemented [`docs/0.2.0_REVIEW.md`](0.2.0_REVIEW.md) (a
filesystem-integrity pass); the work now sitting on `main` unreleased
implements [`docs/0.2.1-release-review.md`](0.2.1-release-review.md) (a
release-process pass, scored 9.1/10 overall, "would not pull or reissue").
There is no third review to work from, and the review that exists lists
one open item.

So 0.3.0 is the first release the project chooses the contents of. It
should pay the two debts that only a minor release can pay — the frozen
egui stack and the Windows size accounting the last review left open —
fix the one thing a user can be stuck inside (a scan that cannot be
stopped), and close the last real WinDirStat parity gap (a scan is one
root, and WinDirStat opens on a drive picker).

The same three gates hold at the end of every sprint, as in
[`docs/0.2.1_PLAN.md`](0.2.1_PLAN.md): `cargo fmt --all -- --check`,
`cargo clippy --all-targets --all-features -- -D warnings`,
`cargo test --all-features` — so a half-finished sprint can be committed
and handed off. Windows `cargo test` runs the unit tests only; verify the
unix-gated side in WSL before pushing.

---

## Sprint 0 — cut `v0.2.2` first

Not part of 0.3.0, but it should happen before 0.3.0 starts.

`Cargo.toml` still says `0.2.1` and no `v0.2.2` tag exists, while `main`
carries the entire release-process rewrite: `--release <version>` mode on
the changelog generator, the inverted tag ordering in `CONTRIBUTING.md`,
pinned `cargo-deb` / `cargo-cyclonedx`, and the real
`actions/attest-sbom` binding. **None of that has ever run against a real
tag.** The whole point of the change was that the tagged tree carry a
finished changelog, and the only way to know it does is to cut a release
with it.

Do that on a patch release with nothing else in it, so a failure is
unambiguous. If it goes wrong at 0.3.0 instead, the failure is entangled
with a release that also moved the GUI toolkit.

### Done when
`v0.2.2` is tagged and published; the tag's own source archive contains a
`## [0.2.2]` section, not `## [Unreleased]`; the published assets carry
provenance *and* an SBOM attestation that `gh attestation verify`
accepts.

## Sprint 1 — leave egui 0.29 behind

The largest and riskiest item, so it goes first, on its own branch, with
nothing else in flight. `CLAUDE.md` already describes the shape of it —
measured against 0.36: 135 compile errors, three subsystems redesigned
rather than renamed.

**Why now.** `deny.toml` ignores four advisories. Two of them
(`RUSTSEC-2026-0194`, `RUSTSEC-2026-0195` — quick-xml, reached through
`zbus_xml` via `atspi`, the Linux accessibility stack) are live
vulnerabilities whose fix is a breaking quick-xml release, which means
bumping accesskit, which means bumping egui. They cannot be cleared any
other way, and every release that ships with them ships a `deny.toml`
that says "revisit when egui 0.29 is left behind". Dependabot is also
frozen to patch on the whole egui group for the same reason.

### Tasks

1. **Pick the target version**: the newest egui/eframe that still has a
   working wgpu backend, and confirm `egui_extras`' table API survives
   (`Column::remainder`, the resizable/`claims_width` behaviour the
   column rules depend on). Note in the branch what was chosen and why.
2. **Commit one: the mechanical pass.** `Rounding` → `CornerRadius`
   (`u8`, not `f32` — the rounding constants change type),
   `Frame::none()` → `Frame::NONE`, the extra `StrokeKind` argument on
   the painter's rect calls. This is renaming; it should leave the tree
   compiling except for the three redesigned subsystems.
3. **Commit two: the draw path.** `eframe::App::update(ctx, frame)`
   becomes `ui(ui, frame)`, so everything currently threading a
   `Context` threads a `Ui`. `SidePanel`/`TopBottomPanel` collapse into
   one `Panel::left/right/top/bottom(id)` taking a `Ui`.
4. **Commit three: the menus.** `menu::bar` and `close_menu` (29 call
   sites) are gone, replaced by `MenuBar`/`MenuButton`/`MenuConfig`.
   Four rules in `CLAUDE.md` describe an API that will no longer exist —
   `set_menu_style` having to run inside `menu::bar`, the square
   menu-bar highlights, the zero vertical panel margin, the column-based
   menu rows. Re-derive the *intent* (a highlight that fills the strip,
   shortcuts in their own column) against the new API and rewrite those
   paragraphs; `menu_bar_highlights_are_square_and_fill_the_bar` and
   `menu_rows_align_and_keep_shortcuts_off_their_labels` get rewritten
   with them, not deleted.
5. **Clean up behind it**: drop the two quick-xml ignores from
   `deny.toml` and re-check whether ttf-parser and paste are still
   reached; unfreeze the egui Dependabot group from patch-only; rewrite
   the "held at 0.29" section of `CLAUDE.md` to describe where the stack
   actually is.

### Done when
- Both binaries build and run on Linux, macOS, and Windows, **with a
  person watching the window** — this is the one sprint whose regressions
  a test suite cannot be trusted to catch alone.
- `src/gui/ui/tests.rs` passes with the menu tests re-derived rather
  than removed.
- `cargo deny check` passes with two fewer ignores.

### If it stalls
This sprint is the release's schedule risk, and it is all-or-nothing —
there is no half-migrated state worth shipping. If it is not converging,
abandon the branch and ship 0.3.0 from sprints 2–5; the advisories stay
ignored and the paragraph in `deny.toml` gets a date. Do not let it hold
the other four hostage.

## Sprint 2 — a scan you can stop

`scanner::Progress` carries `files`, `dirs`, and `bytes` and nothing
else. `duplicates::DupProgress` has had a `cancelled: AtomicBool` since
0.2.1, checked between candidates — the scanner never got one. So a
mistyped root, a network share, or `C:\` on a spinning disk has to be
waited out: the GUI keeps the previous tree interactive, but the worker
keeps every core but one busy until it finishes, and closing the window
leaves it running.

### Tasks

1. **A cancel token on the scan.** Add `cancelled: AtomicBool` to
   `Progress` (it is already the shared, lock-free thing both front ends
   hold) and check it where the counters are updated — once per
   directory, in `finish_dir`/`scan_dir`, so it costs a relaxed load per
   directory rather than per entry, matching the existing contention
   argument for the counters.
2. **Say "cancelled", not "failed".** `scan_with_options` returns a
   `ScanOutcome` (`Completed(Tree)` / `Cancelled`) inside its `Result`
   rather than folding cancellation into `Err` — a cancel is not an
   error and must not surface as one in either front end's status line.
3. **Free the partial tree off the UI thread.** The abandoned subtree
   goes through `gui::app::scan::drop_in_background`, same as any other
   released tree. The TUI drops on its own thread already; check it does
   not join on the scan.
4. **Wire both front ends.** GUI: a Cancel button on the progress splash
   and `Esc`; the shortcut must be one `handle_shortcuts` knows about.
   TUI: `q`/`Esc` during `progress_splash`. Neither asks for
   confirmation — a cancelled scan destroys nothing.
5. **Exit while scanning** signals cancel and does not block the UI
   thread waiting for the worker.
6. **Tests.** Cancel a `deep_chain` scan mid-walk and assert it returns
   `Cancelled` without having walked the whole chain; assert no partial
   tree reaches the app state; assert a cancelled scan leaves the
   previous tree selected and intact in the GUI.

### Done when
A scan of a whole volume can be stopped from both front ends and by
closing the window, and the app is responsive immediately after.

## Sprint 3 — one handle per directory on Windows

This closes the last open item from the release review: whether Windows
"physical size" should mean true allocated size (its Option A) or keep
the compression/sparse-aware definition (Option B, which 0.2.2 took by
documenting it). Option B was the right *patch* answer. 0.3.0 can afford
Option A, and doing it collects three other things in the same call.

`GetFileInformationByHandleEx` with the `FileIdBothDirectoryInfo` class,
called on a directory handle, returns per entry: attributes, logical
size, **allocation size**, **the volume-relative file id**, timestamps,
and the name. The scanner currently gets those from three different
places — std metadata, `GetCompressedFileSizeW` for the files whose
attributes say compressed or sparse, and `file_id_from_handle` recovered
at *hash* time in `duplicates.rs` — and gets allocation size from
nowhere.

Be honest about the payoff: **the speed win is small** (std's `DirEntry`
already caches the `FindFirstFileW` data, so there is no per-entry
`stat` to remove). The win is correctness — cluster-accurate physical
size, and hard-link identity available at scan time instead of only for
files the duplicate hasher happens to open.

### Tasks

1. **Safe leaf wrappers in `platform.rs`**, to the rules the file already
   follows: an owning handle wrapper with `Drop`, one `unsafe` block per
   FFI call containing the call and nothing else, `// SAFETY:` stating
   the argument-validity reasoning, `MaybeUninit` for the buffer. The
   buffer holds variable-length entries chained by `NextEntryOffset`;
   walking it is arithmetic and therefore lives *outside* the `unsafe`
   block, reading through a wrapper that bounds-checks against the
   returned length.
2. **Fall back, never fail.** Some redirectors and non-NTFS filesystems
   do not support the info class. On any failure the scanner drops back
   to the current std path for that directory — a scan that returns
   worse numbers beats a scan that returns none.
3. **Feed the tree**: `physical_size` on Windows becomes allocation size
   where the enumeration supplied it; `Node.file_id` is populated at
   scan time on Windows, so `duplicates.rs` stops needing
   `file_id_from_handle` (keep the function — it is the fallback path's
   answer).
4. **Volume identity**: with a volume serial for the root, Windows has a
   device identity for the first time. Decide and implement one of: make
   `--cross-filesystems` mean something there, or keep it a documented
   no-op on the grounds that reparse points already stop the walk (they
   do — junctions and volume mount points come back as symlinks from
   std, and `a_junction_is_scanned_as_a_link_not_followed` pins it). The
   flag's help text has to match whichever is chosen.
5. **Rewrite the README's physical-size paragraph.** It currently
   explains at length why cluster accounting is deliberately not paid.
   After this sprint that paragraph is false.

### Done when
- A 1-byte file on NTFS reports one allocation unit in physical mode; a
  sparse or NTFS-compressed file still reports less than logical; a test
  pins both (`fsutil`-marked sparse file, as the 0.2.1 test did).
- Hard-linked files are identified without the duplicate hasher.
- Scan wall-clock on a large volume is measured and not worse; the number
  goes in [`docs/PERFORMANCE.md`](PERFORMANCE.md).

## Sprint 4 — more than one root

The parity document lists rustdirstat as matching all three WinDirStat
1.1.2 views. The gap it does not mention is what WinDirStat shows
*first*: a selection dialog offering a folder, one drive, several drives,
or all local drives. rustdirstat scans exactly one path — CLI positional
defaulting to `.`, GUI folder picker.

This is the release's headline user-visible feature, and also the one to
cut if sprint 1 runs long: it is the only sprint here whose value does
not decay by waiting for 0.4.0.

### Tasks

1. **Model.** `Tree` is `{ root_path, root, volume_free, volume_total }`
   — one path, one volume's free space. Multiple roots need a synthetic
   root node over N real roots, with free/total *per root*, and
   `path_for` starting from the owning root rather than a single
   `root_path`. About 56 `root_path` call sites, plus `node_for`,
   `csv_export`, `report`, `duplicates`, and both treemaps' free-space
   tile.
2. **Do not double-count free space.** Two roots on one volume
   contribute one volume's free space, not two — key the free-space
   tiles by volume identity, which sprint 3 supplies on Windows and
   `st_dev` already supplies on Unix.
3. **Restore-by-name carries its root.** The GUI's zoom/selection
   restore captures name components; with several roots those components
   are only meaningful against the root they came from.
4. **GUI**: a drive-picker page in the existing modal — *not* an
   `egui::Window`, per the one-modal rule — listing local volumes with
   free/total, multi-select, plus the existing folder picker.
5. **CLI**: accept several positional paths, and decide whether
   `--all-local-drives` earns its place. Watch the interaction with
   `--csv` and `--no-tui`, which already `conflicts_with` each other;
   `tests/cli.rs` gets the new combinations.
6. **Config**: the remembered last scan becomes a list.

### Done when
Scanning two drives at once produces one treemap covering both, correct
per-volume free-space tiles, working search/duplicates/CSV across the
union, and a rescan that restores the view.

## Sprint 5 — distribution breadth

Small, mechanical, and last. The install story today is "download an
archive" plus a `.deb` and the Nix flake; `rpm` and AppImage were left
open by choice in 0.2.1.

- rpm and AppImage from the existing Linux build job, pinned the way
  `cargo-deb` and `cargo-cyclonedx` now are.
- A winget manifest and a Homebrew formula/cask, both pointing at the
  release archives and their `.sha256` files.
- An AUR `PKGBUILD`.
- Decide on crates.io: `cargo install rustdirstat` would work (two
  binaries, no path dependencies) — check the name is free and that
  publishing a GUI crate is wanted at all.

Code signing and macOS notarization stay out: they need paid
certificates that cannot live in the repository, which is the same
reason they were out of 0.2.1.

### Done when
The README's install section lists more than one way in per platform,
and each is verified by actually installing from it once.

## Explicit non-goals

Named so they are decisions rather than omissions, and carried into
[`docs/ROADMAP.md`](ROADMAP.md) so they outlive this plan:

- **A tree that fills in live during the scan.** WinDirStat does this;
  rustdirstat shows counters and keeps the previous tree interactive.
  Publishing partial trees needs a snapshot protocol that does not
  violate "nothing tree-sized in a draw call". 0.4.0 at the earliest.
- **Inode-deduped tree-wide physical totals.** Still per-pathname, which
  is WinDirStat parity; a tree-wide inode set costs real memory on a
  drive-sized scan. Duplicate *reclaimable* accounting is already
  hard-link aware, which is where it matters.
- **User-defined cleanup commands** (WinDirStat's "Cleanups"). A
  shell-execution surface in an app whose other buttons delete files
  wants a threat model written before any code.
- **Localization.** Both front ends are English-only and nothing is
  wired for translation.
- **Signed installers.**

## Sequencing

1. Cut `v0.2.2` (sprint 0) and confirm the release machinery.
2. Sprint 1 on its own branch. Merge or abandon before anything else
   starts — it touches every file in `src/gui/ui/`, and rebasing sprints
   2–4 across it would be worse than waiting.
3. Sprints 2 and 3 in either order; they do not overlap (`scanner.rs` +
   both front ends' splashes vs `platform.rs` + the Windows scan path).
4. Sprint 4 after 3, so it can use the volume identity that sprint 3
   supplies.
5. Sprint 5 whenever the rest is frozen.

Then release per [`CONTRIBUTING.md`](../CONTRIBUTING.md): version bump
commit, `cargo run --example changelog -- --release v0.3.0` committed
*before* any tag exists, PR with the required checks green, merge commit
(never a squash), annotated tag on the merge commit, push the tag.

## Handoff notes

- Commit only what you changed, by name; the tree may hold another
  agent's in-flight work.
- Sprints 1 and 4 are both wide (every GUI drawing file; ~56 `root_path`
  sites). Grep before resuming rather than trusting a mental map.
- Sprint 3 is `cfg(windows)` and invisible to a Linux CI run; sprint 2's
  cancellation tests are not, and should be written platform-neutral.
